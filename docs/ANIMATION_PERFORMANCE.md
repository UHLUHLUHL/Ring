# 동영상 → GIF / WebP 개선

기준: `ec60fc455422106f0a0e165e531a7ceb7e1a1c87`. 외부 실행 파일이나 새 런타임 의존성 없이 기존 AVFoundation, ImageIO, 정적 libwebp를 사용한다.

## 동작

- 변환 패널을 열면 비디오 트랙의 nominal FPS를 읽어 기본값으로 표시한다. 없으면 최소 프레임 간격의 역수, 정보를 읽지 못하면 30fps를 사용한다. 메타데이터를 읽는 동안 사용자가 선택한 값은 덮어쓰지 않는다.
- 24 / 30 / 60fps 프리셋과 원본 FPS 복원 버튼을 제공한다. 소수점 FPS를 입력할 수 있다. FPS와 최대 변 입력칸은 모두 72pt다.
- 변환 한도는 60fps, 1,800프레임, 최대 변 1920px다. 60fps를 넘는 원본은 원본 값을 표시하고 지원 범위의 값을 선택하도록 안내한다.
- GIF는 프레임별 팔레트 계산과 디더링을 병렬 처리한 뒤 순서대로 기록한다. 누적 시각을 10ms 단위로 양자화해 15fps / 4초가 4.2초로 늘어나던 문제를 수정한다.
- WebP는 첫 프레임 묶음의 변화량이 큰 경우 작은 구간을 병렬 인코딩하고 순서대로 결합한다. 작은 움직임, 적은 프레임, 목표 용량 지정에서는 연속 인코딩으로 프레임 간 압축을 유지한다. 첫 묶음으로 판단하므로 정적인 도입부 뒤에 큰 움직임이 나오는 영상에서는 가속 기회를 놓칠 수 있다.
- WebP의 중복 키프레임 후보 계산을 끈다. 병렬 구간의 시작 프레임은 독립적이며 q85 / method2 기본값을 유지한다. 구간 경계가 바뀌므로 이전 WebP와 동일한 픽셀이나 파일 크기를 보장하지 않는다.
- 전체 재변환 전에 시작·중간·끝의 짧은 표본으로 목표 용량을 추정한다. 최종 바이트 수 검사를 유지하며 실패하면 재시도하거나 출력을 폐기한다. 표본 추정은 용량 보장이 아니다.

## 자원과 정확성

- Apple Silicon과 Intel에서 공통 알고리즘을 사용한다. 발열·저전력·동시 작업 수에 따라 인코딩 작업자 수를 줄인다. 특정 아키텍처의 GPU 기능에 의존하지 않는다.
- 다음 묶음의 추출과 현재 묶음의 인코딩을 겹친다. 두 묶음의 추출/팔레트 픽셀 버퍼에 총 128MiB의 계산상 예산을 두고 활성 애니메이션 작업끼리 나눈다. 이는 프로세스 RSS 상한이 아니다. 코덱 내부 버퍼와 최종 압축 데이터는 별도다.
- AVFoundation 일괄 추출이 같은 원본 프레임을 중복 요청할 때 실패할 수 있다. 실패한 시점만 개별 추출로 재시도하며 고정 FPS라는 가정으로 요청 시각을 바꾸지 않는다.
- WebP가 정적인 구간을 단일 이미지로 축약해도 애니메이션 지속 시간을 복원한다. 완전히 정적인 단일 프레임 결과도 재생 시간을 유지한다.
- 출력의 처음·중간·끝 프레임을 디코딩하고 모든 프레임의 크기·지연, 전체 재생 시간을 검사한다. 기존 OutputTransaction으로 취소·실패 시 미완성 결과가 게시되지 않게 한다.
- GIF의 10ms 지연은 일부 뷰어에서 100ms로 보정된다. 따라서 60fps GIF의 실제 표시 속도는 뷰어에 따라 달라질 수 있으며 UI에서 WebP를 안내한다. [Chromium 구현](https://chromium.googlesource.com/chromium/src/+/HEAD/third_party/blink/renderer/platform/graphics/deferred_image_decoder.cc).

테스트는 15/24/30/60fps, 소수점 원본 FPS, 회전·구간 선택, 목표 용량, 정적인 WebP, 병렬 구간 경계의 픽셀/순서, GIF 직렬 기준 픽셀, 취소·실패 시 정리, 원본 SHA-256 보존을 검사한다. 테스트 결과의 모든 프레임을 디코딩한다.

Intel용 테스트는 Apple Silicon 호스트에서 Rosetta로 실행했다. 실제 Intel 하드웨어의 속도·발열은 별도 검증이 필요하다. HDR, 가변 FPS의 불규칙한 긴 공백, 4K 장시간 영상 전체를 망라한 품질 검증은 아니다.

## 2026-10-21 최종 구현 실측

Apple M5 / 16GiB / macOS 27.0.1, Swift `-O`와 C `-O3`. H.264 1280×720 / 30fps / 4초 합성 영상, 출력 15fps, 조건별 3회 중앙값이다. 열기부터 출력 파일 쓰기까지 측정하며 출력 검사도 포함한다. 기준 실행 파일은 위 커밋의 엔진/코덱 설정을 보존한 연구용 실행 파일이다. 측정 시작·종료의 thermal state는 모두 nominal이고 저전력 모드는 꺼져 있었다. FPS 기본값 변경의 영향을 제외하기 위해 양쪽 모두 같은 15fps를 지정했다.

| 조건 | 형식 | 기준 | 개선 | 배속 |
|---|---|---:|---:|---:|
| 640px · 이동 질감 | GIF | 0.995s | 0.485s | 2.05× |
| 640px · 이동 질감 | WEBP | 0.770s | 0.263s | 2.92× |
| 640px · 고정 배경/작은 물체 | GIF | 0.684s | 0.383s | 1.79× |
| 640px · 고정 배경/작은 물체 | WEBP | 0.226s | 0.256s | 0.88× |
| 1280px · 이동 질감 | GIF | 2.541s | 1.677s | 1.52× |
| 1280px · 이동 질감 | WEBP | 3.569s | 0.928s | 3.85× |
| 640px · 2MB 목표 · 이동 질감 | GIF | 1.384s | 0.422s | 3.28× |
| 640px · 2MB 목표 · 이동 질감 | WEBP | 0.991s | 0.494s | 2.01× |

고정 배경 WebP는 165,174 → 159,702바이트로 3.3% 작아졌지만, 0.226 → 0.256초로 약 30ms 느렸다. 모든 영상이 빨라진다고 보장하지 않는다. 이 경로는 작은 변경 영역의 압축과 제한된 선행 읽기를 우선한다.

용량 제한이 없는 GIF 비교에서는 전체 디코딩 픽셀 해시가 같았다. 프레임 지연 수정으로 재생 시간은 4.2초에서 원본의 4초가 된다. 목표 용량 경로는 결과 해상도/FPS가 서로 다르므로 동일 픽셀 비교가 아니다. WebP 병렬 구간은 손실 압축 결과가 달라질 수 있다. 실제 영상과 Intel 기기에서 이 배속을 보장하지 않는다.

원본 측정 로그와 모든 프레임 디코딩 결과: `.work/animation-implemented-bench/{small,large,target}/{baseline,current}.log`, 집계: `.work/animation-implemented-bench/summary.json`. 개발용 미리보기에서 원본 FPS, 세 프리셋, 원본 복원, 두 입력칸 너비/단위 정렬을 확인했다. 성능 측정 단계에서는 앱을 설치하지 않았다. 이후 `/Applications/Ring.app`에 설치하고, 빌드/설치 실행 파일의 SHA-256 일치, 유니버설 아키텍처, 코드 서명, 앱 실행과 Finder 확장 활성화를 확인했다.
