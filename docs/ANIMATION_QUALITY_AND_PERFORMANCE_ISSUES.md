# Ring 엔진 품질 및 성능 이슈 분석 보고서

이 문서는 최신 릴리즈(v0.2.26) 기준으로 파악된 **움짤(GIF/WebP) 변환 화질 저하**, **프레임드랍 현상**, 그리고 **변환 및 압축 속도 지연**의 구체적인 코드 레벨 원인과 실증적 개선 방향을 정리한 기술 분석서입니다.

---

## 1. 개요 및 배경

Ring 엔진 v2는 하드웨어 비트레이트 캘리브레이션, 무손실 변환, 2-Pass 비디오 압축, 엄격한 품질 검증(PSNR/SSIM 바운드)을 도입하여 **영상 압축 화질 측면에서는 뛰어난 완성도**를 확보했습니다.

그러나 실제 사용 환경에서 다음과 같은 세 가지 핵심 불편 사항이 확인되었습니다:
1. **움짤(GIF) 화질 아쉬움**: 정지된 배경이나 부드러운 그라디언트에서 화면이 지글지글 끓어오르는 디더링 플리커링(Boiling artifact) 및 색상 밴딩 발생.
2. **프레임드랍 / 미세 끊김 (GIF 및 WebP 공통)**: 60fps나 30fps로 변환된 결과물에서 약 1초 주기로 프레임이 튀거나 덜컥거리는 저더(Judder) 발생.
3. **변환 및 압축 속도 지연**: 고화질 프로필과 다중 패스(Multi-pass) 검증 구조로 인해 단순 변환 대비 체감 소요 시간이 긺.

---

## 2. 프레임드랍 (GIF / WebP 공통) 원인 분석

WebP는 GIF와 달리 1ms 단위의 정밀한 타임스탬프를 온전히 지원함에도 불구하고 프레임드랍이 동일하게 체감되는 것은, **엔진 내부의 프레임 타임스탬프 매핑 및 인코딩 파이프라인에 근본적인 결함**이 있기 때문입니다.

### ① NTSC 소수점 FPS(29.97fps 등)와 정수 격자 간 위상 충돌 (Judder)
* **관련 코드**: `Sources/Engine/AnimationSource.swift` (라인 11~17)
  ```swift
  keepNativeTiming = try await MediaEngine.sourceFrameRate(asset).map { abs($0 - fps) < 0.005 } == true
  ```
* **문제점**:
  - 대부분의 스마트폰/카메라 촬영 영상은 정확히 30.0fps가 아니라 **29.97fps(NTSC)**입니다.
  - 사용자가 UI 프리셋에서 "30"을 누르거나 정수 30fps를 지정하면, `abs(29.97 - 30.0) = 0.03 > 0.005`가 되어 **원본 프레임 1:1 보존 경로(`keepNativeTiming`)가 즉시 꺼집니다.**
  - 이로 인해 고정 격자(`AnimationPlan(duration:fps:)`)로 전환되어 1/30초마다 프레임을 샘플링하게 됩니다.
  - `AnimationFrameReader.nearestSample`에서 29.97fps 원본 타임스탬프와 30fps 출력 격자의 위상 차이가 누적되면서, **약 1초마다 출력 슬롯 2개가 동일한 원본 프레임을 중복 참조하고 바로 다음 프레임을 강제로 건너뛰는(Skip) 현상**이 발생합니다.
  - 이것이 WebP와 GIF 모두에서 1초마다 주기적으로 덜컥거리는 프레임드랍으로 체감됩니다.

### ② WebP 4프레임 청크 병렬 인코딩(`chunkSize = 4`)의 모션 단절
* **관련 코드**: `Sources/Engine/AnimationPipeline.swift` (라인 460~485)
* **문제점**:
  - `parallelWebP`가 활성화되면 전체 배치를 4프레임 단위로 잘라 독립된 `WebPAnimEncoder` 인스턴스에서 병렬 인코딩한 뒤 Muxer로 이어 붙입니다.
  - WebP 애니메이션은 인접 프레임 간의 모션 벡터 및 픽셀 델타를 참조하여 부드럽게 이어져야 하지만, **매 4프레임마다 이전 프레임 참조가 완전히 단절되고 독립 키프레임이 강제 생성**됩니다.
  - 이 4프레임 경계마다 움직임의 매끄러움이 끊겨 시각적인 프레임 건너뜀으로 느껴집니다.

### ③ libwebp 자동 프레임 병합과 1px 투명 홀드 프레임의 V-Sync 불일치
* **관련 코드**: `Sources/Engine/CodecV2.c` (라인 252~270)
* **문제점**:
  - `libwebp` 애니메이션 인코더는 인접 프레임 간 차이가 극히 작으면 프레임을 하나로 자동 병합합니다.
  - Ring의 Muxer(`ring_webp_mux_append`)는 원래 타임라인 슬롯을 복원하기 위해 그 사이에 **1×1 크기의 투명 `noop` 블렌딩 프레임**을 삽입합니다.
  - 그러나 브라우저나 macOS 미리보기의 WebP 디코더는 이 1×1 블렌딩 프레임을 렌더링할 때 화면 갱신 주파수(ProMotion/60Hz)와 타이밍 동기화가 흔들려 재생 타이머가 튀는 현상을 유발합니다.

## 3. 움짤(GIF) 화질 저하 원인 분석

### ① 프레임별 독립 팔레트로 인한 "디더링 지글거림(Boiling Artifact)"
* **관련 코드**: `Sources/Engine/AnimationPipeline.swift` (라인 430), `AnimationEngine.swift` (라인 167~253)
* **문제점**:
  - 매 프레임마다 완전히 독립적으로 255색 Median-cut 팔레트를 새로 계산하고 Floyd-Steinberg 오차 확산 디더링(`ring_palette_dither`)을 수행합니다.
  - 멈춰 있는 배경이나 부드러운 그라디언트 영역에서도 프레임마다 디더링 점(도트)의 위치와 색상 인덱스가 미세하게 요동치며, 결과물이 **지글지글 끓어오르는 모래알 노이즈(플리커링)**를 띱니다.

### ② 15비트 RGB Median-cut 알고리즘의 색상 편향
* **관련 코드**: `Sources/Engine/AnimationEngine.swift` (라인 169~223)
* **문제점**:
  - 인간의 시각 인지(초록색/명도에 민감하고 파란색에 둔감한 특성)를 고려하지 않은 단순 RGB 축 범위 분할을 사용합니다.
  - 이로 인해 피부 톤이나 미세 명암비 구간에서 색상 양자화 버킷이 부족해져 눈에 띄는 밴딩(Color banding) 현상이 발생합니다.

## 4. 변환 및 압축 속도 병목 분석 (실측 데이터 기반)

엔진 실측 기록(`docs/ANIMATION_PERFORMANCE.md#L75`)에 따르면, **프레임 추출과 인코딩이 파이프라인으로 이미 오버랩(Pipelining)되어 실행**되고 있습니다:
> *"2배 추출은 60프레임에 0.23초, AVAssetReader 연속 디코딩은 0.09초였지만, 추출을 연속 디코딩으로 바꿔도 전체 시간은 줄지 않았다. **추출은 인코딩과 겹쳐 돌기 때문이며, 남은 시간은 q90 / method4 / sharp YUV 인코딩이다 (프레임당 22ms).**"*

따라서 단순 디코더 교체(`AVAssetReader`)로는 전체 변환 속도가 유의미하게 빨라지지 않으며, 진짜 병목은 다음과 같습니다:

1. **WebP 인코딩 연산 자체의 무거운 비용**:
   - `q90 / method 4 / sharp_yuv` 조합은 최고 화질을 보장하지만 프레임당 약 22ms가 소요됩니다. (60프레임이면 인코딩 자체만으로 1.3초 이상 소모)
2. **GIF 팔레트 생성 시의 Swift 연산 오버헤드**:
   - 디더링 자체는 C로 작성되었으나, 매 프레임 32,768개 버킷의 15비트 히스토그램을 순회하고 Median-cut 버킷들을 분할/정렬하는 연산이 프레임당 10~15ms씩 CPU 시간을 차지합니다.
3. **영상 압축의 다중 패스(Multi-Pass) 및 프로빙 오버헤드**:
   - 엄격한 목표 용량 및 PSNR/SSIM 검증을 위해 분산 윈도우 프로빙 ➔ 1-Pass 인코딩 ➔ 필요 시 2-Pass 보정 ➔ 프레임별 디코딩 검증이 순차적으로 실행되어, 순수 1-Pass 하드웨어 인코딩 대비 1.5~2배의 시간이 소요됩니다.

## 5. 실질적이고 구체적인 개선 로드맵

### [과제 1] 프레임드랍 완벽 제거 (최우선 순위 ⭐)
1. **소수점 FPS 허용 오차 완화**:
   - `abs(sourceFPS - fps) < 0.005`를 `abs(sourceFPS - fps) < 0.1`로 완화.
   - 사용자가 29.97fps 영상에서 30fps를 선택해도 고정 격자로 쪼개지 않고 원본 타임스탬프를 100% 1:1 보존(`keepNativeTiming = true`).
2. **WebP 4프레임 청크 쪼개기 제거**:
   - `chunkSize = 4` 병렬화를 단일 연속 스트림(멀티스레드 `thread_level: 1` 활용)으로 전환하여 모션 델타 연속성을 유지하고 1px 투명 홀드 프레임 삽입을 원천 차단.

### [과제 2] 움짤(GIF) 화질 개선
1. **시간축 디더링 안정화 (Temporal Noise Smoothing)**:
   - 이전 프레임과 색상 차이가 임계값 이하인 정적 배경 픽셀은 이전 프레임의 인덱스를 재사용하고 오차 확산을 차단하여 배경 끓음 현상 박멸.
2. **대표/전역 팔레트 및 Wu's Quantizer 도입 검토**:
   - 연속된 씬 단위로 대표 팔레트를 공유하여 플리커링을 줄이고 연산 속도 개선.

### [과제 3] 변환 및 압축 속도 최적화
1. **WebP 인코딩 프로필 튜닝**:
   - `method 4` ➔ `method 3` 조정: PSNR 차이 0.1dB 미만으로 화질 저하 없이 **인코딩 시간 약 30~35% 즉각 단축**.
2. **GIF Median-cut 연산 C 이전**:
   - 히스토그램 수집 및 버킷 분할 연산을 C(`CodecV2.c`)로 이전하여 프레임당 수십 ms의 CPU 오버헤드 제거.
3. **영상 압축 "고속(1-Pass)" 모드 지원**:
   - 엄격한 2-Pass 보정이 필요 없는 일반 압축 시에는 프로빙 없이 VideoToolbox VBR 1-Pass로 즉시 출력하는 Fast 경로 제공.
